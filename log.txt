# 3. The Most Important Design Decision: Rules Engine + AI

I recommend a **hybrid AI architecture combining deterministic rules, evidence retrieval, structured AI extraction, and a verification engine**.

Do not make the entire decision using an LLM prompt.

An LLM is useful for interpreting unstructured evidence, such as logs, PDFs, screenshots, and database exports. However, the final deletion status and output structure must follow explicit rules.

For example, suppose an evidence file contains:

```text
2026-10-20 11:42:10
Email: rahul@example.com
Action: Delete customer profile
Result: Success
```

An LLM might interpret this as proof that the customer's data has been deleted.

But the log proves only that a particular operation reported success. It does not prove that the record is currently absent, that other copies have been handled, or that the data cannot be recreated.

Your system must distinguish between:

- **Claim:** A deletion operation reported success.
- **Evidence:** A record or system state was observed.
- **Conclusion:** The evidence establishes whether the policy requirements are satisfied.
- **Action:** A remediation or verification operation is required.

This separation is the foundation of a trustworthy solution.

# 6. Stage 2 — Build an Identity Resolution Engine

This is one of the most important parts of the project.

Suppose a customer originally registered with:

```text
user_id: U-1042
email: old@example.com
phone: 9876543210
```

Later, the customer changed their email:

```text
user_id: U-1042
email: new@example.com
phone: 9876543210
```

The deletion request arrives for:

```text

```

If you search only for the current email, you might miss records associated with the old email.

## 6.1 Construct an identity graph

Represent identity relationships as a graph.

```text
                   user_id: U-1042
                    /     |      \
                   /      |       \
           old email   new email   phone
               |          |          |
               v          v          v
          Old support   Account    Analytics
           records      records     records
```

Each relationship must be supported by evidence.

For example:

```json
{
  "canonical_user_id": "U-1042",
  "identifiers": [
    {
      "type": "email",
      "value": "old@example.com",
      "valid_from": "2025-01-01",
      "valid_to": "2026-04-12",
      "source": "user_audit_log.csv"
    },
    {
      "type": "email",
      "value": "new@example.com",
      "valid_from": "2026-04-12",
      "valid_to": null,
      "source": "user_identities.csv"
    }
  ]
}
```

This is an illustrative internal representation, not an output format required by the challenge.

### How to implement it

Start with deterministic matching:

1. Find the current user using the request email.
2. Resolve the stable internal user ID.
3. Read the user's historical identity changes.
4. Collect all verified historical identifiers.
5. Find associated records across the supplied evidence.
6. Track the source of every identity relationship.
7. Preserve uncertainty when multiple identities could match.

Use normalized email matching and exact internal identifiers where appropriate.

Do not merge people solely because their names match.

Likewise, do not automatically associate an arbitrary email hash with a person unless the available evidence establishes that relationship.

### Why this is scalable

The same identity-resolution logic can be reused across every deletion request. Cache the resolved identity graph where it is safe to do so, and invalidate cached results when relevant identity evidence changes.

For the hackathon, a relational representation or in-memory graph is sufficient. You do not need a dedicated graph database to demonstrate the concept.

Your `deletion_rules.csv` should control how every relevant data category is handled.

## 8.1 Different data categories require different treatments

## 8.2 Build a deterministic policy interface

# 9. Stage 5 — Reconstruct the State at `audit_at`

This is where your solution can become significantly better than a simple search-and-delete agent.

The problem statement says that the agent must determine the resource state at `audit_at`, using the available evidence. It also explicitly states that reported workflow statuses and operation results are claims, not proof. problem_statement

## Example

Suppose the evidence contains these events:

| Timestamp | Event |
|---|---|
| 10:00 | Account deletion requested |
| 10:05 | Account record deleted |
| 10:10 | Synchronization job started |
| 10:12 | Synchronization job restored an old record |
| 10:15 | Dashboard marked deletion complete |
| 11:00 | Audit performed |

The deletion workflow reports success, but the current state is incomplete because the synchronization process restored the data.

Your agent should reconstruct the timeline, identify the surviving record, and determine the required remediation.

## Recommended algorithm

For each case:

1. Resolve the current and historical identifiers.
2. Collect relevant evidence and operational events.
3. Normalize timestamps and sort events chronologically.
4. Establish the latest trustworthy state for each resource.
5. Evaluate whether the evidence supports that state at `audit_at`.
6. Detect contradictions between operational claims and observed states.
7. Apply the deletion policy to the reconstructed state.
8. Determine whether active processes or restore paths remain capable of recreating the data.

### Avoid a common mistake

Do not simply choose the last event in a log and assume it describes the current state.

A later event may be a dashboard update, a failed operation, or an unrelated activity. You need to interpret the event type, its outcome, and the evidence available for the resource.

For high-confidence decisions, prioritize direct state evidence over unsupported workflow claims.

When evidence is insufficient, the agent should not fabricate proof of completion. Define a conservative, evidence-aware decision policy and validate it against the supplied sample outputs.

## 10.2 Recommended remediation order

For an incomplete deletion, the agent should produce a dependency-aware plan.

1. Disable the process that can recreate the deleted data.
2. Block affected restore paths where required.
3. Delete records that must be removed.
4. Redact records that must be retained without direct identifiers.
5. Anonymize records that must remain but must no longer be linkable to the user.
6. Verify that deleted records are absent.
7. Verify that retained records remain available and compliant.
8. Verify that active data flows are disabled.
9. Verify that affected restore paths are blocked.

This is an illustrative planning sequence. The final sequence must also follow the challenge's allowed-operation ordering and any dependencies in the evidence.

**Why stop data flows first?**

If you delete records before disabling an active process that recreates them, your remediation may immediately become invalid.

# 13. How to Make It Scalable and Efficient

You have 518 deletion cases to process. That is a manageable workload for a well-designed local Python pipeline.

You do not need an elaborate distributed architecture just to handle this dataset.

Instead, design the application so that it can scale later.

## 13.1 Process evidence once, reuse it across requests

A naive solution might reopen every PDF, parse every log, and call an LLM for every case.

That wastes time and model tokens.

Use this pipeline:

```text
Evidence Files
      |
      v
One-Time Ingestion
      |
      v
Normalized Evidence Store
      |
      v
Identifier Index
      |
      v
Per-Case Retrieval
      |
      v
Policy and Decision Engine
```

Parse each evidence file once, where possible.

Store normalized records with their original source references. Then retrieve relevant evidence for each deletion case.

## 13.2 Cache expensive AI extraction

For unstructured evidence, cache extraction results using a key based on:

```text
file_hash
+ extraction_prompt_version
+ model_version
+ extraction_schema_version
```

If the file and extraction configuration have not changed, reuse the result.

This avoids paying repeatedly to extract the same information.

## 13.3 Use small models selectively

Use deterministic parsers for structured files.

Use a model for genuinely ambiguous evidence, such as:

- Interpreting a complex log entry.
- Extracting details from a screenshot.
- Resolving conflicting descriptions in a document.
- Converting unstructured evidence into a validated JSON object.

A useful fallback strategy is:

```text
Evidence
   |
   v
Can a deterministic parser extract it?
   |
   +---- Yes ----> Parse and validate
   |
   +---- No -----> AI extraction
                       |
                       v
                 Schema validation
                       |
                 +-----+-----+
                 |           |
               Valid       Invalid
                 |           |
                 v           v
            Normalize     Retry or flag
```

Do not send every case to a large model merely to classify it as complete or incomplete.

## 13.4 Parallelize independent work

Once the ingestion layer is complete, many evidence extraction and per-case operations can run independently.

You can use bounded concurrency for I/O-heavy parsing and model calls.

However, avoid excessive parallelism that creates API rate-limit errors or memory pressure.

For a local hackathon implementation, Python multiprocessing, asynchronous execution, or a small worker pool may be enough, depending on the workload.

Record usage during the actual final run rather than estimating it afterward.

### Do you need LangGraph?

If you use LangGraph, use it to orchestrate meaningful stages, such as evidence retrieval, identity resolution, policy evaluation, and verification. Do not add agents simply to make the architecture look more advanced.

# 16. The Evaluation Strategy That Can Improve Your Score

Do not wait until the end to evaluate the solution.

Your uploaded problem statement says that scoring considers status accuracy, identity resolution, discovered records and risks, evidence citations, policy decisions, and the completeness and ordering of steps. It also requires an evaluation report with case-level, step-level, field-level, and sequence accuracy, plus at least three additional test cases. problem_statement

You should therefore evaluate several layers independently.

## 16.1 Stage-by-stage evaluation

| Evaluation layer | What to measure |
|---|---|
| Status classification | Accuracy and per-class precision, recall, and F1 |
| Identity resolution | Correct current and historical identifier coverage |
| Evidence retrieval | Relevant-record recall and precision |
| State reconstruction | Accuracy of resource states at `audit_at` |
| Policy evaluation | Correct treatment for each data category |
| Data-flow analysis | Precision and recall for active recreation risks |
| Step generation | Correct operation, state, system, resource, and evidence ID |
| Sequence evaluation | Whether steps follow the required order |
| CSV validation | Correct schema, case count, uniqueness, and sorting |

### Why status accuracy alone is insufficient

Suppose your agent correctly identifies a case as `INCOMPLETE` but misses an active restore path.

The final status might be correct, yet the remediation plan remains unsafe and incomplete.

Conversely, the agent might identify every remaining record but classify a case incorrectly because it mishandles a retention rule.

Evaluate each component separately.

## 16.2 Use sample outputs as your first benchmark

Start with the provided sample requests and expected outputs.

Your workflow should be:

1. Parse the sample dataset.
2. Run your agent.
3. Compare its output with the expected output.
4. Identify which fields differ.
5. Trace each failure to its responsible component.
6. Fix the underlying logic.
7. Run the tests again.

Do not hardcode the sample answers or map particular case IDs to known labels.

Use the samples to test generalizable rules.

## 16.3 Create at least three additional test cases

I recommend creating synthetic tests covering different failure modes.

**Test A: Historical identifier survives**

The current email is absent, but a previous email remains in a record that must be deleted.

Expected behavior: detect the record and propose the policy-required remediation.

**Test B: Synchronization resurrects data**

The primary record is absent, but an active synchronization process can recreate it.

Expected behavior: detect the active flow and include the required prevention and verification steps.

**Test C: Retained record contains prohibited identifiers**

A policy-required record must remain, but it still contains an email address that must be removed.

Expected behavior: redact the record instead of deleting it, then verify that the record remains available and complies with policy.

These are proposed synthetic tests. Their expected outputs should be derived from the policy rules and the challenge's operation-ordering requirements.

You can add further tests for incomplete evidence, conflicting timestamps, and backup restoration.

# 17. The Correct Evaluation Metrics

I recommend reporting more than one overall score.

## A. Status accuracy

\[
\text{Status Accuracy} =
\frac{\text{Correctly classified cases}}
{\text{Total cases}}
\]

This measures whether the agent predicts `COMPLETE`, `INCOMPLETE`, and `NOT_APPLICABLE` correctly.

Also report per-class precision, recall, and F1. A high overall accuracy can hide poor performance on an uncommon class.

## B. Field-level accuracy

Measure how often generated step fields match the expected output:

- `phase`
- `system_id`
- `resource_id`
- `operation`
- `state`
- `evidence_id`

Use a consistent definition of field-level accuracy and document how missing or extra steps are handled.

## C. Step-level accuracy

Evaluate whether each expected step appears correctly, including its operation, resource, state, and evidence reference.

A robust implementation should also report extra predicted steps because false findings can be just as problematic as missing findings.

## D. Sequence accuracy

Measure how often the ordered steps match the expected sequence.

Two outputs can contain identical operations but differ in sequence. That matters because the challenge explicitly requires ordered steps.

## E. Evidence quality

Measure the percentage of findings and verification steps that reference valid, relevant evidence.

You should also measure unsupported claims and false-positive findings.

## F. Policy compliance

Measure whether the system:

- Deletes records that must be deleted.
- Redacts records that must be retained without prohibited identifiers.
- Anonymizes records where required.
- Preserves required records.
- Prevents known recreation paths.

For the evaluation report, document the metrics, their formulas, the test methodology, observed failures, and improvements made.

# 18. The Most Important Edge Cases

These are the cases I would explicitly test before submitting.

| Edge case | Expected reasoning |
|---|---|
| Current email absent, historical email remains | Resolve historical identity and investigate the surviving record |
| Primary record deleted, secondary copy remains | Deletion is incomplete |
| All records appear absent, but a sync process remains active | Deletion is incomplete if the process can recreate prohibited data |
| Backup contains deleted information | Apply the actual backup and restore policy; do not assume every backup must be physically deleted |
| Retained record contains prohibited identifiers | Redact or otherwise apply the required policy treatment |
| Required retained record is missing | Investigate whether required retention has been violated |
| Deletion operation succeeded, but no reliable current-state evidence exists | Do not treat the operation's success message alone as proof |
| Evidence contradicts the reported status | Resolve the contradiction using trustworthy state evidence |
| Person did not request deletion | Return `NOT_APPLICABLE` with `[]` |
| Historical identifiers cannot be reliably associated with the person | Preserve uncertainty rather than making unsupported identity matches |

The last point is particularly important. A false identity match could cause your agent to recommend modifying another customer's records.

For an actual production system, ambiguous identity matches and irreversible operations should require an appropriate authorization or human-review mechanism.

# 19. An Improved Approach: Evidence-Driven Planning

Here is the main improvement I would make beyond a basic AI deletion agent.

Instead of letting the LLM directly write the final JSON array, have it produce structured findings and let a deterministic planner generate the output.

### Step 1: The AI interprets the evidence

It extracts candidate records, identifiers, timestamps, operational events, and relevant context.

### Step 2: The evidence validator checks the extraction

It verifies that:

- The evidence source exists.
- The identifier is supported.
- The resource and system are valid references.
- The timestamp can be interpreted.
- The extraction matches the required schema.

### Step 3: The policy engine evaluates each record

It determines the required treatment and whether the observed state satisfies the policy.

### Step 4: The dependency analyzer identifies recreation risks

It examines active flows, imports, and restore paths.

### Step 5: The decision engine determines the case status

It evaluates the complete set of requirements rather than relying on a single finding.

### Step 6: The planner creates an ordered plan

It produces only the operations permitted by the challenge's schema and rules.

### Step 7: The verifier checks the plan

It validates required actions, retained records, evidence references, and step ordering.

### Step 8: The output generator writes the CSV

It serializes the steps into JSON and validates the final file.

The resulting architecture looks like this:

```text
              Raw Evidence
                   |
                   v
             AI Extraction
                   |
                   v
            Evidence Validation
                   |
                   v
            Identity Resolution
                   |
                   v
            Temporal Evaluation
                   |
                   v
              Policy Engine
                   |
                   v
           Data-Flow Dependency
                   |
                   v
             Decision Engine
                   |
                   v
          Deterministic Planner
                   |
                   v
           Output Verification
                   |
                   v
               output.csv
```

**Why is this better?**

Because the AI is responsible for interpreting information, not inventing the final result.

Your decision-making logic becomes reproducible, testable, and easier to improve when the evaluation report identifies a failure.

# 21. What I Would Avoid

There are several tempting approaches that I would not use.

### Mistake 1: Using only an LLM prompt

A prompt such as "Read all files and decide whether deletion is complete" is difficult to reproduce and evaluate.

Use structured extraction followed by deterministic policy evaluation.

### Mistake 2: Trusting the dashboard status

The challenge exists precisely because reported deletion status can be misleading.

Use the evidence to establish the current state.

### Mistake 3: Searching only for the current email

Historical identifiers can reveal surviving records that current-identity matching misses.

### Mistake 4: Deleting every remaining record

Some records must be retained. The correct action depends on the supplied policy.

### Mistake 5: Ignoring active processes

Removing existing data does not solve the problem if a synchronization or restoration process can recreate it.

### Mistake 6: Hardcoding the expected outputs

The challenge explicitly prohibits hardcoded test labels and file-specific answers.

Your logic must work for unseen cases.

### Mistake 7: Optimizing for status accuracy alone

A correct status with missing evidence or an incomplete remediation plan can still receive a poor score.

### Mistake 8: Adding unnecessary infrastructure

Do not spend your limited hackathon time deploying multiple services, databases, or orchestration platforms before the core audit logic works.

Build a reliable local pipeline first.
